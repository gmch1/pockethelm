# 开发与交接流程

默认由 Codex 直接完成需求、实现、验证、review 和发布，不自动委派给 ZCode 或其他 AI。只有用户明确指定委派或跨模型协作时，才按其要求分工。以一份任务文档保留需求、执行及验收记录。

## 分工

| 工作 | 负责人 | 交付内容 |
| --- | --- | --- |
| 需求拆解 | Codex | 用户目标、范围、验收条件、必要约束 |
| 实现和自查 | Codex | 产品代码、必要测试、实现说明 |
| 自动化和真机验证 | Codex | 结果、设备与环境摘要、可复查证据、待发布 APK |
| 代码 review | Codex | 集中提出的问题及复查结论 |
| 修复 review 问题 | Codex | 按编号回复，补充修复后的验证 |
| 发布 | Codex | 包与测试证据核对、商店更新及下载校验 |

## 一份任务文档

复制 [任务模板](tasks/TEMPLATE.md) 到 `docs/tasks/`，文件名使用日期和简短主题。一个任务聚焦一个完整问题，或几个共享状态与验证步骤的相关问题。无关修改另开任务。

任务状态为：待实现 → 实现中 → 待 review → 待修复或 review 通过 → 已发布。无需发布的任务在 review 通过后标为“已完成”。阻塞时记录具体缺少的条件，不把未执行的检查写成通过。

Codex 默认维护整份任务文档。用户明确委派时，指定的执行者维护其实现、验证和修复回复，保留已有意见与证据，避免相互覆盖。需求变化直接更新原文档，注明影响的验收项。

只有存在用户明确授权的委派时才需要跨 agent 交接。交接消息只需要“任务文档路径 + 状态 + 必要阻塞”；接收方先读文档，再执行下一阶段。遇到需求变化、错误操作或确实阻塞时及时沟通。

## 实现与验证要求

1. 完成代码与必要测试，先自行检查 diff、异常路径及测试接线。
2. 运行与改动相关的自动化检查。记录实际命令、通过数、失败数、跳过项及原因；失败后修复并重跑受影响的检查。
3. 在专用 Android 测试机上完成相关真机验证，包括必要的 instrumentation 和真实界面操作。使用隔离数据和专用测试会话，保留用户配对、草稿和已有任务。
4. 需要发布时，验证与发行包名、签名一致的 release APK。测试 APK 仅用于验证，不得作为发行产物；真机结果不能仅依据 ADB 命令的退出码，应检查测试报告和实际行为。
5. 在文档中记录测试对应的代码版本与 APK SHA-256。工作区未提交时，同时标明未提交范围及可核对的源码快照标识，覆盖新增文件，不能只写 HEAD。
6. 记录界面验证步骤与结论，必要时提供日志或截图位置；注明未覆盖的场景。清理自己安装的测试包和临时文件，保留正常 App 及用户数据。
7. 全部必要检查通过后标为“待 review”。无需为了交接主动提交代码，是否提交遵循当前任务要求。

### 测试会话的费用与清理

用户于 2026-11-02 明确要求，Codex 和 ZCode 的真实会话测试均遵守：

- 发送模型请求前核对当前可用模型及费用，选择满足测试必要能力的最便宜模型；未核实费用时不凭模型名称认定最便宜。提示词保持简短，只发送验收所需的最少消息。
- 专用测试会话名称加 `[测试]` 标注，并包含任务主题，便于识别和精确清理。测试不命名分支时，在该断言结束后补上标注。
- 测试结束立即清理本次创建的会话，失败路径也执行清理；仍有运行中回合时先中断并确认结束，再调用引擎原生删除能力。仅取消订阅或隐藏列表不能证明回合停止。
- 若引擎只支持归档，则停止回合并归档，证据中如实区分归档与删除；清理失败明确记录，保留私有定位信息供后续处理，不静默报成功，不触碰正常用户会话。

设备地址、ADB/SSH 入口、签名属性及测试目标从本地部署文档或管理员配置获取。不得把私钥、口令、二维码授权或用户会话内容复制到可公开的任务文档。证据可保存在已忽略的 `.local/` 或仓库外。

用户已授权使用测试机现有 root 直接完成安装、测试授权和界面操作，不等待用户手动点击允许。2026-11-02 又明确要求一次性解决反复授权：本项目测试权限保留为该测试机基线，不再在测试后恢复成 ignore。正常 App 的数据与配对信息保留，其他应用的授权不变。

真机统一入口为 `scripts/android/device_test.py`。安装和运行签名 release 测试示例：

```sh
python3 scripts/android/device_test.py --install \
  --class com.gmch.codexremote.ReadingUiDeviceTest \
  --out "$HOME/.local/state/pockethelm/device-test/instrument.txt"
```

入口通过 root 安装，预授予扫码相机和 MIUI 后台启动权限，并通过系统原生 provider 配置正式包与测试包的双向启动规则。包重装后自动重新应用，避免 UID 变化或 MIUI 清理规则导致再次弹窗；OEM 意外弹窗仅在确认属于本项目测试启动时自动处理。测试结束卸载测试包、清理临时 APK，保留测试权限基线。私有 live fixture 的专项验证也必须复用该预配置，不再使用旧脚本还原 10021/10032 为 ignore。

跨项目的全局授权政策、固件兼容说明及参数化入口见 `/home/ming/projects/ops-notes/runbooks/android-agent-unattended-testing.md`。其他项目使用该手册和 `configs/android-129/agent-testing/android_test.py`，传入自己的包名、APK、权限及测试类；不要复制本项目固定参数。当前执行方式同时受 `~/.codex/AGENTS.md` 全局约定约束：没有用户明确指定时，由当前 Codex 直接完成，不自动委派 ZCode 或其他 AI。

## Codex review 与发布

Codex 审查完整改动、验收覆盖和测试证据，一次汇总可执行的意见。每条问题包含编号、文件位置、触发条件、影响和验收要求；修复与验证记在同一编号下，复查后关闭。用户明确指定其他执行者时，由该执行者补充其修复与验证。

不重复执行已有充分证据且源码未变的整套测试。出现失败、证据缺失、测试版本不一致或尚未解释的风险时，补充有针对性的验证；不因补验而自动委派其他 AI。

发布前，Codex 核对 review 结论、最终代码范围、版本号、包名、签名、不可调试属性，以及待发布 APK 与已测试 APK 的 SHA-256。优先发布原测试产物；重新构建后哈希变化时，先对实际待发布产物完成必要验证。

有发布授权时，Codex 上传到原商店条目，校验商店版本、索引和实际下载包，并填写发布记录。文档变更本身不需要重新发布 App。
