# 借鉴 Agents Anywhere：会话恢复、状态管理与回归验证计划

状态：批次 A 已发布 0.4.26/36，R4–R6 已关闭。批次 B–D 尚未实施；本地提交完成，按用户要求未 push。

## 需求与验收

### 用户目标

分析 Agents Anywhere 中适合 PocketHelm 的设计，形成可分阶段实施的计划。优先改善切后台、断线、重连、切换会话时的可靠性，减少重复请求、旧响应覆盖新状态、错误横幅和重复消息，不以增加功能数量为目标。

预期用户体验：

- 回到前台先看到已有内容和草稿，能够区分“正在连接”“正在恢复会话”和“加载失败”。
- 旧会话或旧连接的迟到响应不会覆盖当前界面；刷新历史不会撤销刚收到的新状态。
- 消息发送结果不确定时先核对，不因自动恢复再次发送任务。
- 操作不可用时说明具体原因，而不是点击后才暴露底层异常。
- 后续修复有稳定、低成本的自动化复现方式，避免依赖临时断网或反复调用模型。

## 实施方案与顺序

### P0：固定现有行为，建立可控的故障测试

优先级：最高。先完成此阶段，再修改恢复逻辑。

1. 梳理两引擎的进入前台、切标签、进入后台、手动断开、重连、切换环境和切换会话入口，记录各自的取消对象与状态更新位置。
2. 扩展现有 FakeRpcBridge 或等价夹具，提供显式的请求进入信号、响应延迟、响应丢弃、连接关闭和迟到响应控制；用事件/闩锁控制顺序，不依赖长时间 sleep 制造竞态。
3. 对不同故障分别记录：请求是否到达、服务端是否执行、客户端是否收到结果、是否持久化回执，不能用单一“抛网络异常”替代全部边界。
4. 可注入时钟、后台宽限和刷新间隔，测试快速覆盖后台超时；正式配置保持现有值。

交付：生命周期与请求清单、故障夹具、现有关键行为的回归。缺陷用例可以在开发阶段展示修复前失败，最终交付不能把失败用例静默跳过。

验收：能稳定复现取消、迟到响应、发送结果不确定和快照竞争；正常失败仍可见，取消异常不进横幅；测试不需要真实模型或关闭测试机网络。

### P1：集中管理恢复流程，分开连接与会话状态

优先级：最高。依赖 P0，是第一批产品改动。

拟引入小型状态模型和协调器，名称可在实现时调整：

- 连接：Disconnected / Connecting / Connected；失败原因单独记录。
- 会话内容：Cached / Restoring / Ready / Failed；没有选中会话时不启动详情恢复。
- 引擎运行状态：Unknown / Idle / Running / Waiting 等，沿用各自原生事实映射。
- 模型、额度、审批等辅助数据分别维护加载和错误，不再由一个全局 busy 决定整页可用性。

恢复顺序：

1. 立即显示已有缓存与草稿，标明需要刷新；不把缓存状态当作当前运行事实。
2. 获取当前连接：仅按下文连接作用域复用建立任务；详情恢复和列表恢复独立调度，不能只凭环境/引擎合并所有恢复请求。
3. 捕获环境身份、连接代次、会话选择版本和目标 ID。后续每次应用结果前校验这些字段。
4. 按引擎契约恢复订阅并读取历史；订阅和读取顺序必须覆盖中间事件窗口，不能先全量读取、后订阅却不做补偿。
5. 合并历史与期间收到的实时更新；运行状态、审批和操作能力分别校准，审批按下文引擎来源表恢复，不能作为内容 Ready 的前置条件。没有原生版本号时采用请求代次及受控事件缓冲，不用墙钟时间猜新旧。
6. 分别结束各数据的加载状态。历史读取失败保留已有内容；额度失败不应使会话历史变成失败。

并发和取消约束：

- 旧任务的 success、catch、finally 都不能修改新任务的状态或清除其加载标记。
- 主动断开后不自动重连；切换环境取消旧任务并隔离缓存和回执。
- CancellationException 继续向上传播，不包装成业务错误。
- 保留现有后台宽限与前台触发规则。首期不引入无限自动重试，也不自动恢复已缺失的原生会话 ID。
- 必须用已知 ID 重新附着的引擎操作属于恢复；不得因此创建替代会话或启动新回合。

验收：连续切后台/前台、重复刷新只产生一套必要恢复操作；会话 A 的迟到响应不能污染 B；手动断开后无后台连接复活；旧内容、草稿和待确认发送记录保留。

#### 恢复任务的作用域与交接（R1）

| 层级 | 合并键 | 目标变化时的处理 |
| --- | --- | --- |
| 连接建立 | 环境 resumeIdentity、引擎、连接意图版本 | 同一有效意图复用；手动断开/环境切换递增意图版本，旧建立结果不得安装到新状态 |
| 会话详情恢复 | 环境、引擎、连接代次、会话 ID、选择版本 | 同键合并；换目标立即使旧任务失效并启动当前目标恢复，不等待旧详情 RPC 正常返回 |
| 列表恢复 | 环境、引擎、连接代次、列表范围/筛选版本 | 与详情恢复分开；列表请求不能吞掉进入会话后的详情请求 |

调度与状态提交由单一调度者或短临界区管理；网络调用不在该临界区中。每个任务保存唯一句柄，结束时仅能 compare-and-clear 自己的句柄。选择版本使 A→B→A 的两次 A 也属于不同恢复任务。每层最多一个当前任务，重复信号合并，不堆积刷新队列。

切换目标后，旧详情任务取消并使所有回调失效，新目标在健康连接上立即调度。若旧操作占住不可取消的底层 I/O，按 R2 关闭/隔离该连接，当前目标要么在新连接恢复，要么在预算内明确失败，不能因等待旧任务而永久 Restoring。环境切换不能复用旧连接或跨环境发送记录。

#### 预算、超时终态及控制操作（R2）

以下是**拟实现的恢复专用预算**，不是现有代码保证；参数通过单调时钟和测试配置注入。只改变协调器发起的连接/恢复请求，不缩短用户模型回合或既有写操作的业务预算。

| 阶段 | 拟定预算 | 完成或到期后的状态 |
| --- | --- | --- |
| 连接建立 | 45 秒总工作预算，包含锁等待、SSH 建立和协议初始化 | 成功进入 Connected；到期结束 Connecting、保留缓存，显示连接超时 |
| 核心详情恢复 | 连接可用后 60 秒总工作预算；单 RPC 上限 45 秒且不超过剩余预算 | 成功进入 Ready；到期结束 Restoring，保留内容/草稿，显示可手动重试的历史恢复错误 |
| 列表恢复 | 连接可用后 45 秒总工作预算 | 到期保留旧列表，结束列表加载并显示局部刷新失败 |
| 辅助读取 | 每个模型/额度/运行状态/interaction 任务 45 秒；最多并发 2 个 | 各自结束加载，保留旧展示并标记未核实或局部错误；不阻塞历史 Ready |
| 失效连接清理 | 独立总预算 3 秒 | 使旧连接不可继续使用；不在主线程或状态锁内等待线程退出 |

deadline 在阶段开始时固定；每次调度/写入/等待前检查剩余预算，不足则结束，不能每个子调用重新获得全额预算。辅助读取只对当前仍需要的目标排队，目标失效即移除，不积压历史目标。冷连接的详情恢复工作预算为 45+60 秒，已连接为 60 秒；触发失效清理时另计最多 3 秒。该口径是软件调度目标，不承诺操作系统极端停顿下的物理实时性。

超时与用户取消必须分开：协调器只把自己的 deadline 到期转为对应阶段错误；生命周期/用户取消向上传播，清理状态但不弹错误。子 RPC 的超时归属在适配层显式标记，不能依赖“都是 CancellationException”统一吞掉。初始化/连接失败路径也适用清理预算。

I/O 和锁的具体约束：

- Protocol.kt 当前的响应等待超时不涵盖 write。实现要给恢复请求覆盖发送锁等待、写入及读取的端到端预算，并由独立 watchdog 执行失效处理；只加 withTimeout 不算完成。
- 核对 JSch/socket/管道的 close 能否实际打断阻塞 I/O，使用可关闭测试流验证读写线程退出；无法证明时不得宣称硬超时已解决。清理线程超预算后隔离连接、报告资源清理失败，在其释放前禁止同引擎重复建立新连接，避免后台线程无限累积。该情形属于有界失败，不是无限加载。
- 历史、列表等网络读取不能长期持有共用 actions 锁。保留写操作之间必要的串行与防重复保护，不能为了拆 busy 而将发送/审批无条件并发。
- 手动断开不排在历史锁之后：立即递增代次、取消调度并启动 transport 关闭。合法的打断/审批只需必要的短状态校验和发送串行，不等待历史读取结束；如果连接/审批身份尚未核实，明确禁用并解释原因，而非隐藏排队。
- 底层输出阻塞时所有写操作可能受影响，此时应关闭失效连接并显式失败，不能承诺仍能发送控制命令。在途写请求若不能证实尚未发送，一律保留结果待确认，禁止自动重发；历史失败本身不代表写请求失败。
- RpcClient 的 onEvent/onResult 在读循环中执行。状态应用回调不能等待需要该读循环返回结果的 RPC，也不能等待由此 RPC 调用者持有的锁，避免恢复协调器引入循环等待。

批次 A 必须完成最小安全的事件交接和现有合并保护，不能等到 P3。优先复用当前按 RPC 流顺序应用快照的机制；确需暂存事件时同时限制条数和字节数，建议初值 512 条/2 MiB。触顶后不丢弃控制事件继续假装恢复成功：标记恢复失效、结束当前尝试并按原生能力重新核实，必要时关闭连接。不得因此自动重发写请求或自动无界重试。具体限制通过夹具证明后可调整并记录。

#### 审批与交互恢复来源（R3）

| 引擎 | 当前有效来源与身份 | 重连/无法恢复时的处理 |
| --- | --- | --- |
| Codex | 当前连接实际收到的 server-initiated request；身份包含连接代次和保留原始类型的 request ID，并核对会话/回合归属 | 断开立即使旧卡片失效；只有当前连接收到的新请求，或已取证确认的原生重新交付，才能操作；不从历史、缓存或工具条目恢复旧 request ID |
| ZCode | 现有 recoverInteractions/readGuarded 等路径调用的原生 interaction 权威接口；保留其原生 ID、会话/工作区及已有版本/状态校验 | 重连后重新读取当前交互，合并/关闭过期项；无法读取标为未核实并禁用响应，不重放旧回答 |

统一的是 UI 表达，不是伪造一个两引擎通用的审批列表 RPC。Codex 若没有可枚举的原生接口，不把“等待读取审批列表”加入恢复流程，也不因当前没有审批事件就断言服务端不存在待处理事项。需要用户处理但无法重新取得权威请求时，提示在原生客户端核对。

审批状态独立于内容状态：读取失败/无法重建不阻塞历史 Ready。提交回答前再校验连接、目标及当前卡片有效性，服务端拒绝仍权威；其他客户端已处理或回合结束后关闭卡片。已回答但回执丢失进入结果待确认，不自动同意、再次回答或转发到新连接。重连后相同值的 request ID 只有收到新的权威请求才算新卡片，绝不能复用旧回答意图。

### P2：统一动作可用性与错误表达

优先级：高。依赖 P1，两个引擎分别接入。

为发送、排队、插入、打断、审批响应、附件和模型选择提供统一的动作状态结构，区分“不支持”“暂不可用”“不允许”“状态尚未核实”。结构参考 supported / available / allowed，但允许字段未知，不能把未知直接当 true。

- Codex 与 ZCode 适配器分别依据已核实的协议字段和现有 guard 生成状态，UI 不根据“有一条运行中消息”自行推断可打断。
- 每条状态携带作用域及来源；旧连接的可用状态在重连后失效，直到重新核实。
- 按动作风险处理未知：编辑草稿、阅读缓存继续可用；发送、审批等写操作遵循现有防重复/授权约束，不能借 UI 抽象放宽。
- 状态仅用于提前提示，服务端最后一次校验仍保留；点击与执行之间发生变化时按真实拒绝更新状态。
- 引入结构化 AppError：分类、用户文案、可采取的动作、脱敏技术详情。优先覆盖 DNS、断连、认证/主机指纹、会话不存在、历史读取失败、操作结果待确认。
- 协程取消不是 AppError；详情不输出凭据、配对码、附件内容和完整用户消息。

验收：同一按钮能区分连接未恢复、引擎不支持和权限拒绝；旧能力不覆盖新能力；UnknownHost 等技术错误有明确操作提示；“重试”不能自动重发结果未知的写请求。

### P3：统一时间线身份与历史/实时合并

优先级：中。先取得真实协议样本和 P0 竞争用例，再开始实现。

先整理映射表，说明各引擎的环境、会话、回合、消息/工具原生 ID、内容版本和排序字段。优先保留原生稳定 ID；不得直接照搬其他项目的“类型 + 位置”算法，因为分页、乱序和重排下的位置不一定稳定。

- 同一真实工具调用的开始、结果、历史回读归入同一个条目；不同调用即使正文相同也保留多项。
- 实时与历史走同一映射规则；内容哈希用于判断变更，不作为跨条目去重键。
- 保留 clientId 用户消息对账和 FAILED/UNCERTAIN 语义，以及失败消息原位置显示。
- 明确区分完整替换、分页窗口和增量更新；一页历史没出现某项，不能当作删除该项。
- 连接代次变化后重新核实版本范围，不能跨引擎/跨连接直接比较无可比性的 revision。
- 高频更新先测量后合并批次；只合并同一条目的可替代更新，审批、失败、结束等控制事件不能丢。队列需有界，溢出采用明确重同步，而不是无限占内存。

验收：实时后回读不重复，回读期间的新消息不消失；相同文本的两次调用仍为两项；分页、删除/替换、乱序和重连均有独立测试。

### P4：协议能力明确后再做增量恢复与刷新优化

优先级：中，条件性阶段，不是首期发布承诺。依赖 P3。

先调查 Codex/ZCode 是否提供有稳定作用域、保留期限和失效信号的恢复游标。分页 cursor、客户端计数器和时间戳均不能冒充可重放的事件游标。

- 若协议支持：初次读取快照，后续按游标补偿；只有明确无法恢复时回退快照。提交恢复进度必须晚于数据成功应用；跨进程保存进度时，还须保证对应数据已持久化，不能只保存游标却丢失内容。
- 若协议不支持：继续使用有范围的原生读取和现有刷新机制；同目标读请求合并，避免重复读取。不为追求“增量”另建不完整的本地事件服务。
- 正常实时连接下是否减少轮询，必须先证明原有轮询覆盖的事件已经有可靠替代；不能直接删掉兜底。
- 如引入退避，仅限幂等读取和可取消的连接恢复；对写操作、主机指纹确认、认证失败、手动断开不自动重试。

验收：无变化恢复减少实际 RPC 数量；历史数量增长时不重复读取整段记录；游标失效能正确回退；无漏项、重复发送或永久停留在恢复状态。

#### R4 [P1] Codex 快速返回前台后，被取消的首次读取不会恢复

- 状态：已关闭（实现复查通过）。
- 位置：RemoteViewModel.kt:153–162（foreground）、:189–202（pauseRecovery / background）、:525–533（scheduleRefresh）。
- 触发：打开一个尚未读完历史的会话，RPC 已进入等待时切后台，5 秒内回前台，连接还在 30 秒宽限内。
- 原因：background 取消详情恢复并清除 historyLoading；foreground 随后仅依据离开时长小于 5 秒返回，没有检查刚才是否取消了未完成恢复。20 秒定时任务又只在 selected 为 null 时刷新，因此选中的会话没有后续自动恢复入口。
- 实际复现：129 上的隔离 ViewModel + 真实 RpcClient/管道探针扣留首次 thread/read，执行 background→foreground，再交付旧响应并用后续 RPC fence 确认读循环已处理。读取次数仍为 **1**，状态为 **Cached**、historyLoading=false、items 为空；没有新读取。此时旧请求已取消，返回响应不能补救，用户可能看到空会话展示而非真实历史。
- 修复验收：区分“目标已有成功且仍新鲜的数据”和“恢复被中断/从未完成”。未完成的目标在回前台时必须重新调度，不受短时离开跳过规则影响；辅助读取也需明确取消后如何重启。补小于 5 秒后台、切标签、首次读取以及已有内容刷新中断的回归，并保留成功缓存的正常去重。

- **修复与验证（2026-11-04）**：foreground 仅对已经 Ready 的成功目标应用短时跳过规则；后台暂停保留 Ready，但未完成/失败的目标保持可重试。被取消的模型、额度和列表状态补充任务记录待恢复通道，回前台分别重启，状态补充读取不重新拉取列表。已覆盖首次读取、已有内容刷新、切标签、成功缓存去重及三类辅助读取。正式回归见 RecoveryLifecycleTest（12 项全部通过），详细汇总见下方修复记录。

#### R5 [P1] ZCode 进入会话的模型同步意图在取消后丢失

- 状态：已关闭（实现复查通过）。
- 位置：ZcodeViewModel.kt:252–270（recoverCurrent）、:586–594（open/retryLoad）、:737–739 附近（read 中 selection 更新）。
- 触发：先前选中 model-A，打开原生选择为 model-B 的另一会话；首次读取还未完成时切后台再回来。
- 原因：只有 open 调用 recoverCurrent(useSelection=true)。后台取消它后，foreground、retryLoad、定时轮询使用默认 false，协调器没有持久保留“当前目标尚待完成进入同步”的意图。因此替代读取成功也只更新 currentSelection，不更新发送使用的 selection，更不会执行该入口原本附带的额度刷新。
- 实际复现：隔离探针让第一次 session/read 挂起，后台取消后通过 foreground 发起第二次读取；第二次响应正常、阶段 **Ready**、currentSelection 为 **model-B**，但 selection 仍为 **model-A**。fixture 未执行任何用户模型切换，也没有发送模型请求。
- 影响：会话已显示恢复完成，后续发送参数却仍取上一个会话的模型/计划；这是发送语义回归，不能仅以“历史正确显示”验收。
- 修复验收：把需要完成的进入同步意图纳入目标恢复状态，在取消/超时/手动重试后继续，成功后明确消费；同时保护用户在恢复期间主动作出的新选择，不能盲目以旧响应覆盖。补两个不同模型/计划的会话切换、取消后恢复、失败后重试与期间手动选择测试。

#### R6 [P2] ZCode 的运行时目录任务绑定会话作用域，导航会将其丢掉

- 状态：已关闭（实现复查通过）。
- 位置：ZcodeViewModel.kt:273–281（recoverAux/pauseRecovery）、:388–394（连接后的辅助调度）、:586–612（open/select）。
- 触发：冷连接或手动刷新时 catalog 尚未返回，用户进入另一个会话；providers 还未加载。
