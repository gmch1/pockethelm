### R1 · P2 · 聊天后返回列表仍显示旧状态与旧排序（已关闭）

- 位置：`android/app/src/main/java/com/gmch/codexremote/ZcodeScreen.kt:116-117` 新增的确定状态标签；相关数据加载在 `ZcodeViewModel.kt:200-206`，返回与会话读取在 `ZcodeViewModel.kt:342-375`。
- 触发条件：列表加载时某个旧会话为 `completed`；进入该会话发送新任务，聊天页已通过 `session/read` 读到运行态，再返回列表。反向情况同样存在：列表加载时为 `running`，进入后任务完成，再返回列表。
- 原因与影响：`state.sessions` 只在 `loadProjects()` 中替换；聊天读取仅更新 `selected`、`phase` 等字段，`back()` 既不更新列表缓存也不重载列表，退出聊天后轮询又跳过无选中会话的情况。因此运行中的任务仍可能被标成“已完成”，已结束任务仍显示“执行中”；旧 `updatedAt` 也导致刚产生新活动的会话不前移。只有用户再次点击刷新、重连等才会纠正。新增确定状态文案没有提示这是旧快照，且与 App 已读到的实时状态矛盾。
- 修复要求：保证从聊天返回列表时能取得并展示更新后的状态与活动顺序。可在返回列表时复用现有 `projects` RPC 做一次刷新，无需增加周期轮询或修改进入会话流程；处理刷新失败，避免把旧快照继续作为当前状态呈现。
- 验收要求：覆盖“完成 → 发送 → 运行中返回”和“运行中 → 完成后返回”，以及旧会话产生新活动后排序前移；这些场景不应依赖用户额外点击刷新。补充刷新失败/断线时的展示验证。静态映射与独立排序测试无法覆盖这个数据同步路径。
- 证据范围：依据 ViewModel 全部 `sessions` 写入点、`read()`、`back()` 和 `schedulePoll()` 的代码路径确认；本轮没有重跑真机场景，不将其记录为实机复现。
- 修复与验证：用户在后续任务明确要求 Codex 直接实施与测试，Codex 已在 `back()` 增加一次批量列表刷新并标记快照新鲜度，刷新失败/断线时显示待刷新，过期连接结果丢弃。`ZcodeListRefreshTest` 在真机覆盖完成→运行、运行→完成、旧会话排序前移、刷新失败与离线返回；最终整组 31 项真机测试通过。具体源码与 APK 标识见 [后续任务](2026-11-01-session-reuse-and-reading.md)。

其他核对：已安装 ZCode Server 3.16.3 的 `@zcode/shared/src/zcode-task-types-core.ts` 定义持久化状态为 `running | completed | error`，本次映射覆盖这三种实际枚举；桥接器透传 `status` 与 `updatedAt`，未发现本次改动引入字段不匹配。时间戳归一化和稳定排序在目前上游毫秒时间戳输入下未发现阻塞问题。
